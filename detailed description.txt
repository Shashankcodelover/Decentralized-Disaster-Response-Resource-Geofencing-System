## 1. Why It Is Being Created (The Problem Statement)

During natural disasters (e.g., hurricanes, earthquakes, flooding), physical communications infrastructure is almost always the first casualty:

* **Centralized Cloud Collapse:** Standard disaster management systems rely on centralized cloud services (AWS, Google Cloud). When cell towers fall and local power grids collapse, access to these remote clouds is cut off, leaving field responders completely blind and unable to coordinate life-saving efforts.
* **Resilient State Synchronization:** In disaster zones, internet connectivity is intermittent. Responders lose and regain network access constantly. If multiple responders edit resource counts offline, traditional database synchronization schemas suffer from severe merge conflicts and data overwrite failures, resulting in inaccurate supply allocations.
* **Danger Zone Geofencing Risks:** During floods or chemical leaks, hazard zones expand dynamically. Without automated geofencing, field responders can unknowingly walk directly into active threat zones. Manually monitoring responder coordinates against danger zones is slow and error-prone.
* **Security & Supply Chain Vulnerabilities:** Emergency operations center networks are highly vulnerable to security breaches. Running database servers with unrestricted system access exposes critical logistics nodes to local network intrusion or supply-chain compromises.

## 2. What It Is Going to Solve (The Unique Solution)

Project Mirage provides an exceptionally resilient, decentralized emergency coordination platform built on a **Dual-Mode WebRTC-Express Architecture** backed by **Conflict-Free Replicated Data Types (CRDTs)**:

1. **Turborepo Monorepo Architecture:** Unifies high-concurrency microservices, an interactive web dashboard, and shared geospatial libraries into a single `pnpm`-managed monorepo, accelerating deployment and testing.
2. **Dual-Mode Sync Control Plane:**
   * **Online Mode:** Clients connect directly to Express and Socket.io, scaling horizontally across multiple server nodes using a Redis Pub/Sub event bus.
   * **Offline/P2P Mode:** When cellular networks drop, clients dynamically form a local WebRTC mesh network, using a Socket.io-mediated signaling channel to connect and establish peer data streams.
3. **Deterministic Yjs CRDT Synchronization:** Employs the Yjs framework and the Yata algorithm to merge concurrent offline resource updates. Updates are merged deterministically based on globally unique logical clocks, guaranteeing eventual consistency without a central server.
4. **MongoDB 2dsphere Geofencing:** Utilizes MongoDB geospatial indexes to detect point-in-polygon intersections, triggering real-time alerts the moment a responder crosses a danger zone boundary.
5. **Node.js 22 Experimental Permission Sandbox:** Enforces strict execution rules at the runtime level, restricting the backend process to approved file paths and network endpoints to limit the impact of potential security breaches.

## 4. Fully Detailed Tech Stack

Project Mirage leverages an advanced monorepo stack to guarantee high performance, modularity, and offline resilience:

* **Monorepo Manager (Turborepo & pnpm):** Coordinates fast builds and workspace dependencies across the following workspaces:
  * `apps/api`: Node.js, Express, Socket.io backend.
  * `apps/web`: React 19, Leaflet, Yjs frontend client.
  * `packages/shared`: Shared types and CRDT helpers.
* **Frontend Framework (React 19 & Vite):** High-speed rendering with React v19 state trees and Leaflet maps for geofence rendering.
* **Real-Time Transport (Socket.io & Redis):** Manages websocket connections, scaling horizontally across nodes using the `@socket.io/redis-adapter` over a Redis Pub/Sub cluster.
* **Conflict Resolution Engine (Yjs CRDTs):** Employs the YATA conflict-free replication algorithm to merge concurrent inserts:

$$\text{Commutativity: } \operatorname{merge}(A, B) = \operatorname{merge}(B, A)$$

$$\text{Idempotency: } \operatorname{merge}(A, A) = A$$

This ensures that regardless of the arrival order of sync packets across the WebRTC mesh, every responder's screen resolves to the exact same supply counts.

* **Database Engine (MongoDB with 2dsphere Indexes):** Enforces geospatial checks utilizing local coordinate maps:

```javascript
// DangerZone MongoDB Schema mapping
const DangerZoneSchema = new Schema({
  name: String,
  geometry: {
    type: { type: String, enum: ['Polygon'], required: true },
    coordinates: { type: [[[Number]]], required: true } // Array of coordinates
  },
  severity: { type: String, enum: ['critical', 'moderate', 'low'] },
  active: { type: Boolean, default: true }
});
DangerZoneSchema.index({ geometry: "2dsphere" });
```

* **Experimental Node v22 Sandboxing:** The backend API is strictly isolated at startup using Node's security permission flags:

```bash
node --experimental-permission \
  --allow-fs-read=./src \
  --allow-net=localhost:27017,localhost:6379 \
  src/index.js
```

## 5. Phase-by-Phase Workflow Functional Description

### Phase 1: Geospatial Danger Zone Mapping

1. An emergency operations coordinator draws a hazard polygon on the Leaflet map.
2. The front-end saves this polygon as a GeoJSON coordinate array, sending a POST request to `/api/zones`.
3. The API server stores this record in MongoDB under a `2dsphere` spatial index.
4. The server broadcasts the new zone to all active Socket.io clients, rendering the polygon on every responder's map dashboard.

### Phase 2: Real-Time Geofence Entry Detection

1. Responders carry smartphones running the web dashboard, which periodically updates their GPS coordinates:

$$\text{Coordinate Payload} = \{ \text{lat: } 37.7749, \text{ lng: } -122.4194 \}$$

2. The Express server queries MongoDB utilizing the `$geoIntersects` spatial operator:

```javascript
const matchedZones = await DangerZone.find({
  geometry: {
    $geoIntersects: {
      $geometry: { type: "Point", coordinates: [lng, lat] }
    }
  }
});
```

3. If an intersection is detected, the server immediately triggers a websocket broadcast (`"zone:enter"`) containing the hazard payload.
4. The client's dashboard sounds an alert and displays a high-visibility hazard banner.

### Phase 3: Offline Mesh Network Transition

1. When cellular signals fail, the web clients lose connection to the Express server.
2. The dashboard automatically switches to P2P/Offline mode.
3. Using previously cached signaling data, clients establish direct WebRTC data channels with nearby peers within radio/Wi-Fi range.
4. The mesh network coordinates state synchronization using Yjs documents:
   * Client A edits a resource count, creating a local operation: `ydoc.getMap('resources').set('water', 150)`.
   * Client A serializes this update as a binary array: `Y.encodeStateAsUpdate(ydoc)`.
   * Client A broadcasts this update to all connected WebRTC peers.
   * Peers apply the update instantly: `Y.applyUpdate(ydoc, receivedUpdate)`.

### Phase 4: Re-Establishment and Central Replay

1. When a mesh peer regains internet connectivity, it reconnects to the central Express server.
2. The client re-establishes its Socket.io connection and triggers a reconciliation sync: `/api/crdt/sync`.
3. The Express server merges the peer's accumulated updates into the central database.
4. The server broadcasts these reconciled state updates to all online clients, ensuring the entire network is synchronized.
